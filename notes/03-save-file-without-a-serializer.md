# 03. シリアライザを書かずにセーブデータを保存する

日付: 2026-10-28
Goose: v2026.3 / C++: MSVC 19.44（VS 2022 Build Tools）
環境: Windows 11

## 題材

ゲームのセーブデータです。3種類のデータを1つのファイルに書いて、読み戻します。

| セクション | 型 | 性質 |
|---|---|---|
| プレイヤー | `Player { name: u8[..16], hp: i32, gold: i32, pos: Vec2 }` | 固定サイズ。名前は容量16の inline 配列 |
| インベントリ | `Item { name: u8[varint], qty: varint, cents: varint }` | 可変サイズ。名前は必要なバイト数だけ、数値は LEB128 |
| クエストの木 | `Quest { id: u32, title: u8[..24], done: bool, first_child: Quest&<u32>?, next: Quest&<u32>? }` | 固定サイズ。子と兄弟へのリンクが4バイトの相対オフセット |

| 言語 | ソース |
|---|---|
| Goose | [experiments/save-data/goose/save.goose](../experiments/save-data/goose/save.goose) |
| C++ | [experiments/save-data/cpp/save.cpp](../experiments/save-data/cpp/save.cpp) |

C++ 版は、ゲームの C++ コードでよくある形（`std::string`、`std::vector`、子は添字で持つ、手書きの Writer / Reader）で書きました。

## 結果

### メモリ上のサイズ（＝Goose ではファイル上のサイズ）

| データ | Goose | C++ (MSVC) |
|---|---|---|
| Player 1件 | 33 バイト | 48 バイト（名前が16文字以上ならヒープ確保が追加） |
| Item 3件 | 35 バイト（約12バイト/件） | 144 バイト（48バイト/件） |
| Quest 1件 | 38 バイト | 72 バイト + 子配列と長いタイトルのヒープ確保。7件で88バイト・5回の確保 |

Goose の構造体はフィールドを宣言順に詰めて置き、アライメントのパディングを入れません。Quest の 38 バイトは id 4 + title (1 + 24) + done 1 + リンク 4 × 2 です。
C++ の `std::string` は MSVC では 32 バイトで、15文字までは本体に inline で持ち、それ以上はヒープに確保します。

### ファイルサイズ

| | Goose | C++ |
|---|---|---|
| save ファイル | 375 バイト | 369 バイト |

ほぼ同じです。Goose は title を24バイト固定で持つぶん大きく、C++ は長さを4バイトで書くぶん大きい、という相殺です。
Goose のファイルは「メモリ上のバイト列そのもの」で、C++ のファイルは「シリアライザが組み立てたバイト列」です。

### 書いたコードの量

| | Goose | C++ |
|---|---|---|
| シリアライザ | なし。`players.to_bytes(file)` が1行 | Writer / Reader と、型ごとの write / read 関数。78 行 |
| 読み込み時の検証 | `from_bytes` が組み込みで行う | Reader の長さチェックと、子の添字が範囲内かの検査を手書き |
| ファイル全体 | 198 行（うち壊す実験が約40行） | 222 行 |

Goose 側で書いたのは、セクションの区切り（ULEB の長さ + 本体）を読む `load_section` の約8行だけです。

### 壊したファイルを読ませる

| 操作 | Goose `from_bytes` | C++ 手書き Reader |
|---|---|---|
| リンク（相対オフセット）の1バイトを反転 | 拒否（false、要素0） | 拒否（添字の範囲検査を書いたので） |
| データ（done フラグ）の1バイトを書き換え | 受理。root の done が true になる | 受理 |
| 末尾を1バイト切る | 拒否 | 拒否 |
| Item の画像を Quest として読む | 拒否 | （未実施） |

設計文書（`docs/design/serialization.md`）の言い方では、検証するのは**安全性**であって**整合性**ではありません。壊れたリンクは「どこか別のメモリを指す参照」になり得るので拒否し、壊れた数値は「正しい形の木に間違った値が入っている」だけなので受理します。整合性はチェックサムの仕事、と明記されています。FlatBuffers の verifier と同じ線引きです。

C++ 側で同じ安全性を得るには、Reader に長さチェックを入れ、読み終わったあとに添字の範囲を検査する必要があります。どちらも書き忘れると、壊れたファイルは範囲外アクセスになります。

### 読み戻したあと

Goose の `from_bytes` が返すのは普通の配列です。読み戻した `lq` に `add_child(lq, 0, ...)` で push でき、リンクもそのまま辿れました。

## ファイルの中身

Goose が書いた `save.gsav` の先頭です。

```
00000000: 4753 4156 4203 6775 7300 0000 0000 0000  GSAVB.gus.......
00000010: 0000 0000 0000 4600 0000 e204 0000 0000  ......F.........
00000020: 4841 0000 40c0 076d 616c 6c61 7264 0000  HA..@..mallard..
```

- `47 53 41 56`：タグ "GSAV"（自分で書いた）
- `42`：ULEB128 で 66。Player セクションの本体が 66 バイト
- `03 67 75 73 00 ...`：`u8[..16]` の name。長さ 3、"gus"、残り13バイトは未使用
- `46 00 00 00`：hp = 70（i32、リトルエンディアン）
- `e2 04 00 00`：gold = 1250
- `00 00 48 41` `00 00 40 c0`：pos = (12.5, -3.0)（f32）
- `07 6d 61 6c 6c 61 72 64`：2人目 "mallard"

ここに書かれているのは、プログラムが計算に使っていたメモリ上のバイト列と同じものです。

## ハマった点

| 書いたもの | エラー | 直し方 |
|---|---|---|
| `Quest { id: 1, title: "..." }`（done を省略） | `missing initializer for field done of Quest (it has no default)` | `done: bool = false` とデフォルトを宣言する |
| `fn add_child(pool: Quest[>..]&, parent: Quest&, ...)` の中で `cur.next .= node` | `a relative reference must point within the same root as its location (§3.9); this reference is rooted at pool` | 親を `Quest&` ではなく添字 `i64` で受け取り、関数の中で `pool[parent_at]` と解決する。相対リンクの両端が同じ root（`pool`）から派生していることをコンパイラが見える必要がある |
| 失敗時に `var empty: T = []; return empty, false;` | `copying a value of type Quest[>..], which contains self-relative references, is not supported; construct it in place` | `return from_bytes<T>("");` にする。空のスライスの `from_bytes` は「空の配列と false」をその場で構築して返す |

2つ目は、この実験で一番 Goose らしいエラーでした。相対オフセットは「同じ配列の中」でしか意味を持たないので、リンクを張る2つの参照が同じ配列から来ていることをコンパイラが静的に確認します。参照を引数で受け取ると、その参照がどの配列に根ざしているか分からなくなるため、添字で受け取る形に書き直すことになります。

## Rust ならどうなるか（コードは書いていません）

- `serde` の `#[derive(Serialize, Deserialize)]` と `bincode` を使えば、シリアライザは書かずに済みます。依存クレートが2つ増えます。
- 木の子を添字で持つ場合、読み込み後の添字の範囲検査は自分で書きます。serde は型の形を検証しますが、添字が配列の範囲内かは知りません。
- メモリ上のサイズは C++ と同じ考え方（`String` 24 バイト + ヒープ、`Vec` 24 バイト + ヒープ）です。

## 感想

- 「データがそれ自体シリアライズ済みの形」という FlatBuffers の性質を、普通の変数で持てるのが Goose の中核です。スキーマ言語もコード生成も要りません。
- その代わり、構造体の中身が「ポインタなし・宣言順に詰める・リンクは同じ配列内の相対オフセット」という制約の中に収まる必要があります。セーブデータのように「書いて、読んで、辿る」データとは相性が良く、任意のグラフをあとから組み替えるデータには向きません。
